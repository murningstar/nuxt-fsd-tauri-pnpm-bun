# Осмыслить обязательно (обоснование отсутствия компонента confirmation-dialog):

**Ситуация 1**:

Пользователь _целенаправленно_ удаляет какой-то item из списка item'ов (например одну конкретную записку из списка записок).

Перед удалением пользователя спрашивают: "вы точно хотите удалить?" (подтверждение действия).
**Если смотреть на это подтверждение с точки зрения _"что перед лицом у пользователя?"_, то пользователь видит `confirmation-dialog`**

**Ситуация 2**:

Пользователю в процессе его работы высвечивается оповещение о начале самоуничтожении системы в 23:00 и предлагаются две опции: "Хорошо", "Отменить". **По сути, с точки зрения _что перед лицом у пользователя?_ это тоже `confirmation-dialog`**.

**Положняк**:

Получается так, что **в двух ситуациях - намерение** пользователя **разное** (или происхождение confirmation-dialog'а разное), **а компонент один**.

Это значит, что в обеих ситуациях мы бы использовали confirmation-dialog. Но это убирает разделение, которое ожидает психика пользователя. Неожиданности разных категорий уравниваются. А это неправильно.

**Встает вопрос:**

Делать компонент `confirmation-dialog` и прокидывать в него настройки, отвечающие за тип confirmation'а (user-initiated / system-initiated или типа того)?

**Ответ:**

Мы можем так сделать.

**А теперь расширяем контекст:**

В будущем нам может понадобиться функционал, в котором мы захотим, помимо подтверждения и отмены, выбирать ещё какие-то действия. Для этого может придти в голову делать отдельный компонент, такой как action-sheet. И тогда в дизайн системе будут следующие компоненты:

- confirmation-dialog
    - Режим отображения 1 - если вызван умышленными действиями
    - Режим отображения 2 - если вызван неявными действиями (или системными)
- action-sheet - для выбора действий

**Новый положняк:**

А что если нужно дать **на выбор пользователю несколько опций** для обоих случаев: при умышленном действии и для неумышленного события?

**Встает вопрос:**

Добавлять эти опции в режимы для `confirmation-dialog` и удалять action-sheet за ненадобностью?

**Ответ, Финал:**

- Иметь `action-sheet`, принимающий несколько опций и существующий на случай взаимодействия пользователя
- И иметь `alert-prompt`, принимающий несколько опций и существующий на случай, где он вызывается не по намерению пользователя

## Alert

Alert, оповещающей пользователя и не предполагающий никаких действий (отмены или ещё чего-либо) не должен прерывать взаимодействие с приложением. То есть, он должен быть нативно встроен в приложение в виде какого-либо индикатора, нажав на который можно узнать подробности / баннера и т.п.. \*\*Для такого алерта нельзя ни в коем случае использовать `<alert-prompt>` или `<action-sheet>`
